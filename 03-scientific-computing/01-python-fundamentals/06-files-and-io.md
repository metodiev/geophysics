# Files, Text I/O and Data Encodings

Everything a geophysicist analyses arrives as a file, and every file is a
sequence of *bytes*. Text is an interpretation of those bytes, and the
interpretation is called an encoding. Get it wrong and you do not get an error —
you get mojibake, a station called `ZÃ¼rich`, a magnitude that fails to parse on
one row out of a thousand, or a table that is one row longer than it should be.

This lesson is about the boundary between the disk and the program, which is the
boundary where the highest proportion of real data-analysis bugs live. The
demonstration writes a **synthetic** earthquake catalogue, reads it back three
ways, breaks it three ways deliberately, and prints what actually happens.

## Learning objectives

By the end of this lesson you will be able to:

1. **Open, read and write** text files with `pathlib` and with explicit
   encodings, and explain why a default encoding is a portability bug.
2. **Read and write** delimited files with the `csv` module, including quoted
   fields containing the delimiter, and explain what `csv.DictReader` adds.
3. **Distinguish** UTF-8, UTF-8-with-BOM and Latin-1 by their byte sequences, and
   predict which combination of codec and content raises rather than corrupts.
4. **Diagnose** mojibake from its appearance, and explain why it is worse than an
   exception.
5. **Handle** `\n` versus `\r\n` line endings, and state why `newline=""` is
   mandatory for `csv`.
6. **Stream** a file line by line rather than materialising it, and say when that
   choice matters.

## 1. Bytes on disk, characters in memory

A file is bytes. `open()` in text mode decodes bytes into `str` on read and
encodes `str` into bytes on write, and it needs to be told — or it will guess from
the operating system's locale. That guess is the bug:

- On a typical Linux container with `LANG=C`, the default is ASCII. A station
  name with an umlaut then raises `UnicodeDecodeError` on a machine where the
  same script ran fine on the developer's laptop.
- On Windows, the default is frequently a legacy code page, so the same file is
  decoded *differently* rather than failing.
- On macOS it is usually UTF-8, which is why the bug is often discovered only
  when the code is deployed.

The rule: **always pass `encoding=` explicitly** when opening text. The choice for
essentially all geophysical text is `"utf-8"`, with `"utf-8-sig"` for files that
carry a byte-order mark.

Three functions cover the whole vocabulary:

```python
path.read_bytes()                 # bytes, exactly as stored
path.read_text(encoding="utf-8")  # str, decoded
path.open("r", encoding="utf-8", newline="")   # a stream, for large files
```

Paths themselves should be `pathlib.Path` objects, not strings. The demo prints
what a `Path` knows about itself:

```text
  this script      : code/
  catalogue        : 01-python-fundamentals/code/_scratch_io/synthetic_catalogue.csv
  suffix           : .csv
  stem             : synthetic_catalogue
  exists           : True
  resolved parent  : _scratch_io/
```

Three practical consequences. `Path("code") / "data" / "x.csv"` is correct on
every platform while `"code\\data\\x.csv"` is correct on one; `.suffix`,
`.stem`, `.name` and `.parent` mean that "write the output next to the input with
a `.txt` extension" is one expression rather than a string-manipulation exercise;
and `Path(__file__).resolve().parent` is how a script finds its own directory, so
a demo can write its scratch files beside itself instead of in whatever directory
it happened to be launched from. That last idiom is used by every demo in this
module.

## 2. Worked walkthrough: writing and reading a delimited file

The demo begins by generating its own data, which is the only honest way to have
a data set in a lesson. The file is labelled as synthetic in its first line:

```text
  wrote synthetic_catalogue.csv: 35,088 bytes
  first four lines as they sit on disk:
    # SYNTHETIC data generated by files_io_demo.py - not a real catalogue
    event_id,time_utc,latitude,longitude,depth_km,magnitude,place
    SYN00000,2026-03-22T04:51:00Z,-2.579,2.8522,38.98,1.91,Zürich
    SYN00001,2026-06-26T04:59:00Z,6.3467,111.6975,54.65,0.28,Station-01
```

Four details, each of which is a real-world hazard.

**The `#` comment line is a convention, not a standard.** RFC 4180 defines the
delimited format and says nothing about comments. A file with a comment line has
an implicit contract: every consumer must skip it. That contract belongs in a
README beside the data, and the reader must implement it — here, a generator
expression filters lines starting with `#` before `DictReader` sees them.

**The header names the columns and their units.** `depth_km`, not `depth`; a
header that omits units is a file that will be misread once and then defended
forever.

**The `Zürich` row is the encoding canary.** A file that contains one non-ASCII
character is a file that will fail loudly on a mis-configured machine, which is
better than a file that will fail silently. In practice this is why test fixtures
deliberately include an accented name.

**The timestamps are ISO-8601 with a `Z`.** Sortable as text, unambiguous as to
zone, and the format every catalog service emits. Do not invent a date format;
you will be the only one who can parse it.

Reading it back two ways:

```text
  csv.reader gave 502 rows (including the comment and header)
  first data row as a list : ['SYN00000', '2026-03-22T04:51:00Z', '-2.579', '2.8522', '38.98', '1.91', 'Zürich']

  csv.DictReader gave 500 records
  magnitude range : -1.00 to 2.98
  depths          : mean 31.33 km, deepest 60.80 km
  distinct places : 14
```

`csv.reader` yields lists of strings — 502 rows, being 500 events plus a comment
and a header, which is a reminder that "count the rows" is not "count the events".
`csv.DictReader` yields dictionaries keyed by the header, which is what makes the
rest of the script readable: `row["magnitude"]` rather than `row[5]`.

The critical sentence in the demo's own output is this one:

> A *row* is a list of strings and nothing else: no types, no units.

The magnitude range is computed from `float(r["magnitude"])`. Until that
conversion happens, `"2.5" * 2` is `"2.52.5"`, and `row["magnitude"] > 2.0`
raises a `TypeError` against a string rather than comparing numbers. Every CSV
reader in every language has this property; the discipline is to convert once, at
the boundary, into a typed record — which is exactly what the module's complete
program does in [`code/catalog_report.py`](./code/catalog_report.py):

```python
yield {
    "event_id": row["event_id"],
    "latitude": float(row["latitude"]),
    "longitude": float(row["longitude"]),
    "depth_km": float(row["depth_km"]),
    "magnitude": float(row["magnitude"]),
}
```

## 3. Worked walkthrough: quoting

Splitting on commas is the naive reader, and it fails on the first field that
contains a comma:

```text
  written: 'SYN00001,"Zürich, Switzerland",-1.5\r\n'
  read back: ['SYN00001', 'Zürich, Switzerland', '-1.5']
  the comma survived inside the field: True
```

The writer added the double quotes because it had to, per RFC 4180; the reader
removed them and returned the field intact. Note the `\r\n` on the end: `csv`
writes CRLF line terminators by default, as the standard specifies.

Hand-rolled parsing fails here, and it also fails on embedded quotes, embedded
newlines and fields with leading whitespace. Use the `csv` module. The one caveat
is that `csv` is a *delimiter* format, not a schema: it will not tell you that a
column is missing, that a number is unparseable, or that a row has one field
fewer than the header. Validation is yours (lesson
[07](./07-errors-and-debugging.md)).

## 4. Worked walkthrough: encodings, measured

```text
  utf-8       19 bytes  b'Z\xc3\xbcrich 47.3769\xc2\xb0 N'
  utf-8-sig   22 bytes  b'\xef\xbb\xbfZ\xc3\xbcrich 47.3769\xc2\xb0 N'
  latin-1     17 bytes  b'Z\xfcrich 47.3769\xb0 N'
  ascii      FAILS to encode: ordinal not in range(128)
```

Same text, three lengths. UTF-8 uses two bytes for `ü` (`\xc3\xbc`) and two for
`°` (`\xc2\xb0`); Latin-1 uses one byte each; ASCII cannot represent either.
UTF-8-with-BOM prepends three signature bytes. That is the whole encoding story: a
codec is a mapping from characters to byte sequences, and different mappings give
different files.

Now the failure modes, which are the reason to care:

```text
  Add a single en dash (U+2013) and latin-1 fails: ordinal not in range(256)

  Decoding with the WRONG codec does not always raise:
    utf-8 bytes read as latin-1 -> 'ZÃ¼rich 47.3769Â° N'
    latin-1 bytes read as utf-8 -> UnicodeDecodeError: invalid start byte at byte 1
```

- **Encoding that is impossible raises.** Latin-1 has no en dash, so
  `text.encode("latin-1")` raises `UnicodeEncodeError`. Loud, and therefore safe.
- **Decoding UTF-8 as Latin-1 produces mojibake, silently.** Every UTF-8 byte
  sequence is also a valid Latin-1 byte sequence, so `Ã¼` appears where `ü`
  belonged and no error is raised anywhere. This is the dangerous case.
- **Decoding Latin-1 as UTF-8 usually raises.** `\xfc` is not a valid UTF-8
  leading byte, so the decoder reports `invalid start byte at byte 1`. Loud, and
  therefore safe — but note the word *usually*: a Latin-1 file consisting only of
  ASCII bytes decodes as UTF-8 without complaint, which is why the bug hides until
  the first non-ASCII name appears.

Two rules follow. **Never use `errors="ignore"` or `errors="replace"` on scientific
data**: both convert an encoding error into silently corrupted content, and in a
catalogue a corrupted field is a dropped or mis-joined event. And **treat the
mojibake string as a diagnosis**: `Ã¼`, `Ã©`, `â€™` are the signatures of UTF-8
bytes read as Latin-1 (or as Windows-1252), and they tell you exactly which
mismatch occurred.

## 5. Worked walkthrough: line endings

```text
  bytes written with newline='' : b'a\r\nb\nc\r\n'
  read with newline=''          : ['a\r\n', 'b\n', 'c\r\n']
  read with universal newlines  : ['a\n', 'b\n', 'c\n']
```

Three different terminators are in that file — CRLF, LF, CRLF — because the demo
wrote them deliberately. On read:

- **With `newline=""`, the file is presented without translation.** Three lines,
  each keeping its own terminator.
- **In the default universal-newlines mode, `\r\n` and `\r` are translated to
  `\n`.** Three lines, all identical terminators.

Universal newlines is what you want for ordinary text. For `csv` it is *not*,
because a quoted field may legitimately contain a newline, and a reader that has
already translated terminators can mistake an embedded newline for a record
separator. Hence the rule: **`open(..., newline="")` for every `csv` file, on read
and on write.** The `csv` documentation is explicit about it and the failure is
intermittent, which makes it exactly the kind of bug that costs a day.

## 6. Worked walkthrough: streaming instead of loading

```text
  lines counted by iteration : 502
  lines counted by readlines : 502
```

Two ways to count the lines, identical answers, wildly different memory cost.
`sum(1 for _ in handle)` holds one line at a time; `len(handle.readlines())`
materialises the whole file as a list of strings. For a 35 kB file the difference
is invisible. For a 10 GB seismic or gridded-text file it is the difference
between working and running out of memory — and the code that works, the
generator form, is the same length.

This is the doorway to lesson [09](./09-iterators-generators.md), where the
one-line iteration becomes a four-stage pipeline that filters, parses and reduces
without ever holding the file.

## 7. Physical interpretation: file format is metadata, and metadata is physics

It is easy to treat I/O as plumbing. In geophysics it is not, for three reasons.

**Units live in headers, and headers are parsed.** `depth_km` versus `depth_m`,
`magnitude` versus `moment_magnitude`, `latitude` with a sign convention for
south — all of these are decided at parse time and are unrecoverable afterwards. A
program that reads a column and loses its unit has destroyed information that no
downstream analysis can restore, which is why the module's complete program keeps
`_km` suffixes all the way into the report.

**Encodings carry place names and instrument codes.** A catalogue entry for
`Zürich` or a station code containing a non-ASCII character is a real record. A
pipeline that mangles it produces a station that exists in the file and not in the
database, and cross-matching then silently loses events. The loss is invisible:
the analysis runs, the map is drawn, and one station is missing.

**Line structure is record structure.** A CSV file with an embedded newline inside
a quoted field, read with universal-newline translation and a hand-rolled splitter,
produces one fewer record and no error. The row count changes, the statistics
change, and the only symptom is a number that is *slightly* off — the worst kind of
bug in a field where the numbers are the product.

So: state the encoding, state the line-ending handling, state which lines are
comments, and validate the row count against an independent expectation (the
header, a metadata file, a checksum). The module's exercises ask for exactly that
last check, because it is the one that catches all three failures above.

## 8. Assumptions and limits

1. **A file fits in memory or it does not, and you must know which.** The
   demo's file is 35 kB; the streaming section is a demonstration of technique,
   not of need. Choose the technique by the file size you actually have.
2. **`csv` implements RFC 4180, and the world does not.** Real files use tabs,
   semicolons, fixed-width columns, or a mix. `csv.Sniffer` guesses; a guess is
   not a specification, so record the dialect in the README beside the data.
3. **UTF-8 is the right default, not a universal one.** Some legacy archives are
   genuinely Latin-1 or a code page, and a few are mixtures of encodings by
   region. Detect once, record it, and pass it explicitly thereafter.
4. **Timestamps in text are strings until parsed.** Nothing in a CSV implies a
   time zone. The `Z` suffix here is a convention this generator chose; a file
   without it needs a stated zone or the times are ambiguous.
5. **The synthetic catalogue is random with a fixed seed.** Its magnitude range
   (-1.00 to 2.98) and mean depth (31.33 km) are properties of the generator, not
   of the Earth.
6. **`os.fsync` and atomic writes are not shown here; they are lesson
   [10](./10-context-managers-decorators.md).** Writing a file without them risks a
   truncated result on a crash, which is why the module's complete program uses an
   atomic context manager.

## 10. Common mistakes

1. **Omitting `encoding=`.** The default depends on the machine; the bug appears
   elsewhere.
2. **`newline` left at its default for `csv`.** Embedded newlines become record
   breaks, intermittently.
3. **`errors="ignore"`.** Converts an encoding error into silently corrupted data.
4. **Hand-splitting on commas.** Fails on the first quoted field, and fails
   silently if the row still has the right length.
5. **Forgetting to skip comment lines.** A `#` line becomes a record, or crashes
   the parse on one file and not another.
6. **Assuming `readlines()` is fine.** It is a decision about file size; make it
   deliberately.
7. **Writing paths with `+` and `"/"`.** Use `pathlib`; the separator is
   platform-specific.
8. **Leaving the file handle open.** Today it is a `ResourceWarning`; under load
   it is a file-descriptor exhaustion. Use `with`.
9. **Parsing units out of a header by hand every time.** Parse once into a typed
   record and let the unit live in the name.
10. **Trusting the row count.** Count the records and compare against an
    independent expectation; a wrong count is the cheapest detector of a parse
    bug.

## 11. Real-world applications

- **Catalogue ingestion.** FDSN event text, ISC bulletins, regional network
  exports: all delimited text, all with header quirks and encodings. The USGS
  event web service at [earthquake.usgs.gov/fdsnws/event/1/](https://earthquake.usgs.gov/fdsnws/event/1/)
  returns formats that this lesson's techniques read directly.
- **Station metadata.** StationXML is XML, not CSV, but the encoding and
  namespace problems are the same family; ObsPy
  ([docs.obspy.org](https://docs.obspy.org)) handles that layer in module
  [03-10](../10-obspy-and-seismic-data/README.md).
- **Legacy archives.** Decades of gravity and magnetic survey data are stored as
  fixed-width or comma-delimited text with region-specific encodings. Being able
  to read them reproducibly is a research capability, not a chore.
- **Field sheets to databases.** The first step of any field campaign's data
  management is turning a spreadsheet export into a validated, keyed table, which
  is this lesson plus lesson [05](./05-data-structures.md).
