## ★1 — Bytes and exceptions

| Action | Result |
|---|---|
| (a) `"Zürich".encode("utf-8")` | `b'Z\xc3\xbcrich'` — 7 bytes |
| (b) `"Zürich".encode("ascii")` | `UnicodeEncodeError: 'ascii' codec can't encode character '\xfc' … ordinal not in range(128)` |
| (c) `"Zürich".encode("latin-1")` | `b'Z\xfcrich'` — 6 bytes |
| (d) UTF-8 bytes decoded as Latin-1 | `'ZÃ¼rich'` — silent mojibake, no exception |
| (e) Latin-1 bytes decoded as UTF-8 | `UnicodeDecodeError: 'utf-8' codec can't decode byte 0xfc in position 1: invalid start byte` |

The pattern to memorise: **UTF-8 → Latin-1 is silent; Latin-1 → UTF-8 raises.**
Every UTF-8 byte sequence is a valid Latin-1 byte sequence (Latin-1 maps all 256
byte values), so Python has nothing to complain about; `\xc3\xbc` becomes the two
characters `Ã` and `¼`. In the other direction `\xfc` is not a legal UTF-8 start
byte, so the decoder stops.

The exception to (e): a Latin-1 file containing *only* ASCII bytes decodes as
UTF-8 without complaint, because ASCII is a common subset. That is why the bug
hides until the first accented name appears.

## ★2 — The byte-order mark

**(a)** The three bytes `ef bb bf` are the UTF-8 encoding of U+FEFF, the byte-order
mark, so the file was written with `encoding="utf-8-sig"`.

**(b)** Reading with `encoding="utf-8"` returns `'\ufeffStation'` — the BOM is
decoded as an ordinary character and becomes the first character of the text.

**(c)** Reading with `encoding="utf-8-sig"` returns `'Station'`: the codec strips
the mark if present and otherwise behaves as `utf-8`.

**(d)** `'\ufeffStation' == 'Station'` is `False`. A parser that compares a header
field or a station code against a literal loses every record in that file, or
writes a key with an invisible leading character into a dictionary, producing two
distinct keys that print identically. The fix is either to open with
`utf-8-sig` (recommended for files that might carry a mark) or to strip
`"\ufeff"` from the first field explicitly.

## ★3 — Line terminators

**(a)** On Windows in text mode the default translation converts `\n` to `\r\n`, so
the file contains `b'a\r\nb\r\n'`. On Linux and macOS the same statement writes
`b'a\nb\n'`. **The same source line produces different files on different
platforms** — the reason a repository that stores text without normalising line
endings produces spurious diffs.

**(b)** Written literally as `b'a\r\nb\r\n'` on every platform, because
`newline=""` disables translation.

**(c)** Written literally as `b'a\nb\n'` on every platform.

**(d)** Reading (a):
- with `newline=""`: the lines are `['a\r\n', 'b\r\n']` — terminators preserved;
- with the default (universal newlines): `['a\n', 'b\n']` — all terminators
  normalised to `\n`.

For a CSV file, use `newline=""` on both the write and the read. The `csv` module
documents this, and the reason is that a quoted field may contain a newline: if the
reader has already translated `\r\n` to `\n` it can no longer distinguish a record
terminator from an embedded newline, and the record count changes.

## ★5 — Diagnosing mojibake

| Sample | Written as | Read as | Evidence |
|---|---|---|---|
| (a) `ZÃ¼rich` | UTF-8 | Latin-1 (or Windows-1252) | `Ã¼` is the two-character rendering of the UTF-8 bytes `c3 bc` for `ü` |
| (b) `itâ€™s` | UTF-8 | **Windows-1252** | the sequence `â€™` is `e2 80 99`, the UTF-8 encoding of U+2019 (right single quote); byte `0x80` is undefined in strict Latin-1 but maps to `€` in Windows-1252, which is why the rendering differs from the Latin-1 case |
| (c) `SeismologÃ\xada` | UTF-8 | Latin-1 | `í` is `c3 ad`; `\xad` is the C1 control SOFT HYPHEN, which renders as nothing — so the visible garbage is `Ã` plus an invisible character |
| (d) | — | — | |

**(c)** is the important one for debugging: **mojibake can contain control
characters that print as nothing.** A field that appears to be `SeismologÃa` in a
terminal may actually be `SeismologÃ\xada`, and a string comparison against a
hand-typed `SeismologÃa` will fail. Always inspect `repr`, not the terminal.

**(d)** If `Station-01` is correct and `Zürich` is mangled, the file is **not**
uniformly mis-encoded — it is UTF-8 (or similar) and was read with a codec that
agrees on ASCII but not on non-ASCII. Every ASCII-only byte is identical in
UTF-8, Latin-1, Windows-1252 and ASCII, so an ASCII-only file gives no evidence
at all; the presence of one correctly-read non-ASCII field is the counter-evidence
that rules out a global mismatch. The practical conclusion: **a file with no
non-ASCII characters cannot be diagnosed by inspection, and a file with one
non-ASCII character can be diagnosed by that character alone.**

## ★6 — Round trip

```python
import csv
from pathlib import Path

path = Path(__file__).with_name("roundtrip.csv")
rows = [
    {"event_id": "SYN0001", "place": "Zürich", "note": "a,b", "lon": "8.5417"},
    {"event_id": "SYN0002", "place": "München", "note": "plain", "lon": "11.5755"},
    {"event_id": "SYN0003", "place": "Ångström", "note": "x", "lon": "17.6389"},
]
with path.open("w", encoding="utf-8", newline="") as handle:
    handle.write("# SYNTHETIC round-trip fixture\n")
    writer = csv.DictWriter(handle, fieldnames=list(rows[0]))
    writer.writeheader()
    writer.writerows(rows)

with path.open("r", encoding="utf-8", newline="") as handle:
    reader = csv.DictReader(line for line in handle if not line.startswith("#"))
    back = list(reader)

assert back == [dict(r) for r in rows], (back, rows)
print("round trip exact:", back == [dict(r) for r in rows])
print("raw bytes of the quoted field:",
      [line for line in path.read_bytes().splitlines() if b"a,b" in line][0])
path.unlink()
```

**(c)** The assertion passes: every field round-trips exactly, including
`Zürich`, `München`, `Ångström`, and the field `a,b` that contains the delimiter.

**(d)** The raw line reads (approximately)

```text
b'SYN0001,Z\xc3\xbcrich,"a,b",8.5417'
```

The quotes around `a,b` are present because **RFC 4180 requires a field containing
the delimiter, a quote or a line terminator to be enclosed in double quotes**, and
the `csv` module implements that rule. This is the mechanical reason hand-splitting
on commas fails: it is not a matter of style, it is a documented format rule whose
violation produces wrong field counts rather than an error.

## ★7 — A robust reader

```python
from dataclasses import dataclass, field
import csv

@dataclass
class Report:
    accepted: int = 0
    rejected: int = 0
    reasons: list = field(default_factory=list)

    def reject(self, line_number, reason):
        self.rejected += 1
        self.reasons.append(f"line {line_number}: {reason}")

def read_catalogue(path, required=("event_id", "latitude", "longitude",
                                   "depth_km", "magnitude")):
    report = Report()
    try:
        handle = path.open("r", encoding="utf-8", newline="")
    except FileNotFoundError:
        raise
    with handle:
        lines = list(handle)                     # small files only; see lesson 09
    body = [l for l in lines if not l.startswith("#")]
    if not body:
        raise ValueError("no header line found")
    header = next(csv.reader([body[0]]))
    missing = [c for c in required if c not in header]
    if missing:
        raise ValueError(f"header missing columns: {missing}")
    reader = csv.DictReader(body)
    for offset, row in enumerate(reader, start=2):
        if None in row:                          # extra fields -> keyed by None
            report.reject(offset, f"too many fields: {row[None]}")
            continue
        if any(row.get(c) in (None, "") for c in required):
            report.reject(offset, "missing or empty required field")
            continue
        try:
            for c in ("latitude", "longitude", "depth_km", "magnitude"):
                float(row[c])
        except ValueError:
            report.reject(offset, f"unparseable number in {c}: {row[c]!r}")
            continue
        report.accepted += 1
    if body and not body[-1].endswith("\n"):
        report.reject(len(body), "file does not end with a newline (truncation?)")
    return report
```

**(b)** The decisions, with reasons:

| Defect | Action | Reason |
|---|---|---|
| Truncated final line | **Report**, do not raise | One truncated line at the end of a transfer is common and the preceding rows are valid; but the resulting loss must be counted, because a truncated catalogue is missing its last events and event order is often chronological |
| Wrong encoding (UTF-8 decode raises) | **Raise** | There is no correct interpretation of the file, so any output is invented. Never fall back to `errors="ignore"` |
| Row with the wrong field count | **Skip and count** | The row cannot be interpreted field-by-field; the remaining rows can. The count decides whether the result is usable |
| Header missing a column | **Raise** | Every subsequent row would be misinterpreted. This is a schema violation, not a data defect |

The principle: **raise when the *interpretation* is impossible; skip and count when
a *record* is impossible.** Silently repairing a value would be a third category and
is almost never defensible in science.

**(c)** Constructing a file with all four defects:

```python
bad = path.with_name("bad.csv")
bad.write_text(
    "\ufeff# nominal comment\n"                       # BOM + comment
    "event_id,latitude,longitude,depth_km\n"          # missing 'magnitude'
    "SYN1,47.3769,8.5417,10.0\n",
    encoding="utf-8-sig", newline="")
```

The reader raises `ValueError: header missing columns: ['magnitude']` — the
schema violation pre-empts the rest, which is the right order: there is no point
counting row defects in a file whose columns are wrong. Remove `magnitude` from
`required` and the report shows the BOM (`'\ufeff# nominal comment'` is the first
line, so the comment filter misses it — a real and instructive interaction) and the
missing trailing newline.

## ★8 — Classifying a legacy archive without modifying it

The procedure: open each file in **binary** mode, inspect the first bytes, then
attempt decodes in a fixed order, and write the result into a manifest.

**(a)** A byte-order mark is three known bytes at a known offset. It is conclusive
(`ef bb bf` means UTF-8 with a mark), it costs one read of three bytes, and it is
the one signal that a *decoder cannot give you afterwards*, because by the time you
have decoded the file the mark is either stripped or has become a `\ufeff`
character. Checking the bytes first is therefore both the cheapest and the only
lossless test.

**(b)** If a strict UTF-8 decode **fails**, the file cannot be UTF-8: UTF-8 has
strict structural rules (no bare continuation bytes, no overlong forms), so a
failure is conclusive. If it **succeeds**, the file could still be Latin-1 or
Windows-1252 whose bytes happen to be valid UTF-8 — most commonly a file that is
entirely ASCII, which is valid in every one of those codecs. **A decode failure is
proof; a decode success is only a consistent hypothesis.**

**(c)** Adjudicate with *content*: decode as both and compare the results. If they
are identical, the file is ASCII-only and the distinction does not matter — record
`ascii` and move on. If they differ, look at the characters the two decodings
produce: Windows-1252 and Latin-1 differ only in the range `0x80`–`0x9F`, where
Windows-1252 has printable characters (`€`, `“`, `”`, `–`) and Latin-1 has control
codes. A file containing `0x92` that renders as `’` in context is Windows-1252;
a file containing `0x92` in a context where a control character is plausible is
Latin-1. Record the evidence (the byte, its offset, and which rendering is
plausible) rather than the verdict alone.

**(d)** The manifest should record, per file: path, size, SHA-256, whether a BOM
was present, the chosen encoding, the *evidence* for the choice (which decodes
succeeded and which bytes differed), whether the final line ended with a newline,
and the row count if the file is delimited. With a content hash and the evidence,
the classification is reproducible without re-scanning and can be re-verified after
the archive is copied. **Recording the evidence rather than only the conclusion is
what makes the manifest auditable** — otherwise a wrong verdict is
indistinguishable from a right one.
