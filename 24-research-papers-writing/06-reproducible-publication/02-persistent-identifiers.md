# DOIs, ORCID, Persistent Identifiers and Data Repositories

A persistent identifier is an address that is meant to survive the thing it points
at moving. Two questions follow, and this lesson separates them: **is the identifier
well formed?** and **does it resolve?** The first is checkable offline — a check
character detects most transcription errors — and the second is not, which is the
distinction that makes identifier practice testable.

The organising idea is that **identifiers are cheap redundancy**. One extra character
per identifier catches every single-digit substitution and every transposition of
unequal digits in the scheme demonstrated here; without it, every mistyped string is
a legal string. At the scale of a reference list, that difference decides whether a
typo produces an error message or a wrong citation.

> **Data provenance.** All identifiers in this lesson are **SYNTHETIC**, generated by
> the accompanying demonstration. No registry is queried, nothing is resolved and no
> real record is looked up. The check-character algorithm is ISO/IEC 7064 MOD 11-2,
> the scheme used for ORCID iDs; the DOI structural rule quoted is the general
> syntax, not an assigned prefix.

By the end of this lesson you will be able to:

## 1. Persistence is a commitment, not a character string

A URL says where something is now. A persistent identifier says how to *find* where
it is, and it depends on a resolver and an organisation maintaining the mapping. Three
consequences:

- **A DOI is not a URL.** A DOI is often displayed in its resolver form, which is a
  convenience; the identifier itself is the string after the prefix, and that is the
  part to record.
- **Persistence requires upkeep.** A dataset behind a moved page keeps resolving only
  while the landing page is updated.
- **A well-formed identifier can point at nothing.** Structural validity is offline
  and cheap; resolution is online and is the only test of reference.

## 2. Check characters: the arithmetic

The ISO/IEC 7064 MOD 11-2 scheme, as used for ORCID iDs, computes a check character
over the first $15$ digits:

$$\text{total} \leftarrow 0;\qquad
\text{for each digit } d:\ \text{total} \leftarrow (\text{total} + d)\times 2
\bmod 11,$$
$$c = (12 - \text{total} \bmod 11) \bmod 11, \qquad
\text{check} = \begin{cases} X & c = 10\\ c & \text{otherwise.}\end{cases}$$

The demonstration generates $400$ identifiers from this rule; all $400$ validate.

**Detection.** Each identifier is corrupted three ways, $1200$ corruptions in total:

| Corruption | Detected |
|---|---|
| Single-digit substitution | $1200/1200 = 100.0\%$ |
| Adjacent transposition | $1200/1200 = 100.0\%$ |
| Single-digit shift ($+1$) | $1200/1200 = 100.0\%$ |

The scheme is designed for exactly this: alternating weights mean that swapping two
unequal digits changes the total, and a substitution or a shift changes it by a
non-zero amount modulo $11$.

**The comparison.** Without a check character, every corrupted string is still a
legal string:

| Corruption | Corrupted | Detected |
|---|---|---|
| Substitution | $400$ of $400$ | $0$ |
| Transposition | $400$ of $400$ | $0$ |
| Shift | $400$ of $400$ | $0$ |

At $10^{6}$ identifiers with a transcription error rate of $1$ per $1000$ entries,
$1000$ wrong identifiers would go unflagged without redundancy and none would with
it, for the error types tested. That is the entire argument for one extra character —
and the honest limitation: a check character cannot detect a well-formed identifier
that belongs to a different work, and it cannot detect a mistyped identifier whose
typo happens to satisfy the check (about $1$ in $11$ for a random error in the
scheme's own arithmetic).

## 3. What structural validation can and cannot do

Structural rules are offline checks. For a DOI the general syntax is a prefix
`10.NNNN` with $4$–$9$ digits, a slash, and a suffix with no whitespace. Applying that
rule to $300$ synthetic strings generated from six prefixes and six suffixes:

$$101/300 = 33.7\%\ \text{structurally valid}.$$

The invalid ones are invalid for a stated reason — too few digits in the prefix, an
empty suffix, whitespace in the suffix — and the validator can say which. That is
useful in a reference manager and useless as a guarantee:

- **A structurally valid identifier may not exist.** It passed the pattern; nothing
  was resolved.
- **A structurally valid identifier may exist and be wrong.** It may point at a
  different paper — which the check character cannot detect either.
- **A structurally invalid identifier is certainly wrong.** This is the direction the
  offline check is useful for.

The demonstration deliberately never resolves anything: the lesson's claim is about
what offline checks can do, and resolution is a separate act with its own failure
modes (network, rate limits, moved landing pages).

## 4. Which identifier for which thing

| Thing | Identifier | Identifies | Notes |
|---|---|---|---|
| Paper, chapter, report | DOI | The publication, per version | Version DOIs exist for some publishers |
| Person | ORCID iD | A researcher across names and affiliations | Check character; owned by the researcher |
| Dataset | DOI (or repository accession) | The deposit, per version | Cite the version used |
| Software | DOI via a repository, or a version tag | The release | Cite the release, not the project |
| Sample, station, event | Community accession | The object | Conventions vary by community |
| Project | Award or grant number | The funded project | Belongs in the acknowledgements |

Two practices follow. First, **record the version**: a DOI for a dataset often has a
concept DOI (all versions) and a version DOI; cite the version you used. Second,
**record the type**: an identifier without a stated type is ambiguous to a reader
trying to reconstruct a citation.

## 5. Using identifiers in a manuscript

- Put the DOI in the reference list for every work that has one, in the venue's
  format.
- Put dataset and software identifiers in the Data and Code Availability statement,
  with the version and the accession.
- Put the ORCID iDs of all authors in the submission system, and your own on your
  manuscripts' title pages where the venue allows.
- Give every archive and repository a stable link in the text, not a bare project URL.
- Check that each recorded identifier resolves before submission; a dead identifier in
  a data statement is worse than a text description, because it claims persistence.

## Assumptions and regime of validity

1. **The identifiers are synthetic.** No registry is queried, so nothing about real
   identifier assignment, minting or resolution is claimed.
2. **The algorithm is standard, the demonstration is not a validator.** The
   implementation here follows ISO/IEC 7064 MOD 11-2 as used for ORCID iDs; other
   identifiers use other schemes, and a positive check here establishes only that the
   digits satisfy this rule.
3. **The error model is simple.** Real transcription errors include dropped and
   duplicated digits, keyboard-adjacent substitutions and copy-paste truncation, some
   of which this scheme detects and some of which change the length and are caught by
   the length check instead.
4. **The DOI syntax rule is a simplified statement.** The full syntax has more detail,
   and the suffix may contain further structure defined by the registrar.
5. **Persistence is an institutional property.** No check character makes a landing
   page stay online.

## The honest summary

A check character costs one character and catches every substitution, transposition
and single-digit shift in the scheme tested — $1200$ of $1200$ against $0$ of $1200$
without redundancy. Structural validation of DOI-style strings rejects $66.3\%$ of a
deliberately malformed corpus, and guarantees nothing about existence. Record
identifiers with their type and version, and resolve them before submission.

## Common pitfalls

1. **Recording a URL where an identifier belongs.** URLs move; that is the problem
   identifiers exist to solve.
2. **Citing a concept DOI when you used a version.** The reader cannot tell which
   data produced your numbers.
3. **Assuming a valid identifier is a correct one.** Validation is offline; resolution
   is the test.
4. **Omitting software and dataset identifiers.** They are the attribution system for
   infrastructure; see [04 Citation Practice and Attribution](04-citation-and-attribution.md).
5. **Using one identifier for two things.** A release and a project are different
   objects and should be cited differently.
6. **Never re-checking identifiers.** Links rot; a pre-submission check takes minutes.
