# Module 24-06 — Reproducible Publication and Open Data

**Stages:** advanced → research · **Prerequisites:** module
[24-03 Research Methods and Scientific Rigour](../03-research-methods-and-rigour/README.md),
particularly [24-03-04 Reproducible Research Practice End to End](../03-research-methods-and-rigour/04-reproducible-research-practice.md),
and [22-02 Reproducible Research Workflows](../../22-data-engineering-reproducibility/02-reproducible-workflows/README.md).

This module is about turning a result into an artefact someone else can use: a deposit
with the metadata that makes it readable, an identifier that survives the platform, a
code container that runs on a stranger's machine, and a citation practice that records
the dependencies the result rests on. Its organising idea is that **availability and
usability are different properties, and each is measurable**. A deposit can be
downloadable and unusable for want of a licence; a DOI can be well formed and point at
nothing; a notebook can open and not run; a dataset can be used by six hundred papers
and cited by two hundred and fifty.

Each lesson therefore measures its own gap. Metadata completeness averages $64.1\%$ in
the synthetic corpus with a spread of $12.4$ points. A check character catches every
substitution, transposition and shift tested — $1200$ of $1200$ — where an identifier
without one catches none. A $160$-cell notebook has a $77.0\%$ chance of containing a
hidden dependency, and pinning the environment moves total failure by $1.5$ points
while the discipline of a clean run moves it by $26$. Two thirds of software uses and
$58\%$ of data uses leave no citation. The numbers are teaching values; the gaps they
describe are not.

All datasets, identifiers, notebooks and citation counts in this module are
**SYNTHETIC**, generated by seeded demonstrations with chosen parameters. No repository
was queried, no identifier was resolved, no notebook was executed, and no bibliometric
database was searched. Where a lesson states a published convention — the ISO/IEC 7064
MOD 11-2 check-character scheme, the general DOI syntax, preservation-friendly format
categories — it does so as a stated definition, and no external resource is cited.

## Learning objectives

By the end of this module you will be able to:

1. **List** the metadata fields a reusable deposit needs, **compute** a completeness
   score and **model** its effect on reuse.
2. **Classify** file formats by preservation risk and **compute** the share of bytes at
   risk rather than the share of files.
3. **Assemble** a deposit with a manifest, a licence, a pinned environment and one
   entry point that regenerates every reported number.
4. **Compute** and verify an ISO 7064 MOD 11-2 check character and **state** the error
   classes it detects.
5. **Validate** identifier structure offline and **state** what only resolution can
   establish.
6. **Measure** hidden state in a notebook, **separate** it from environment failure,
   and **prepare** a notebook that reproduces from a fresh kernel.
7. **Compute** an attribution gap and **apply** a citation checklist that gives every
   dependency an identifier and a version.
8. **State** what citation counts measure and what they cannot be used to decide.

## Suggested path

**If you are about to submit a paper with data or code:** 01 → 02 §5. Assemble the
deposit, write the availability statement with identifiers and versions, and resolve
every identifier before the deadline.

**If you maintain software or a dataset:** 04 → 02. The checklist and the identifier
practices are what turn use into visible credit, which is the evidence that sustains
maintenance.

**If you work in notebooks:** 03, then 01 §4. The eight-step publication checklist and
the deposit structure together cover the commonest failure modes.

**If you review or edit:** 01 §1 and 03 §3 are the two fastest audits of a
supplementary deposit, and both are offline.

## Mastery checkpoint

1. Score a deposit you have made against the twelve metadata fields and compute its
   completeness.
2. Compute a check character by hand and corrupt the identifier three ways, stating
   which are detected.
3. Run a notebook from a fresh kernel and count the cells with output but no execution
   count.
4. List every dependency of your last paper and mark which are cited with identifiers.
5. Write your Data and Code Availability statement in six lines or fewer, with versions.

## Common pitfalls across this module

1. **Confusing available with usable.** A licence and a format description are not
   optional.
2. **Counting files instead of bytes.** The large files are usually the fragile ones.
3. **Assuming a valid identifier is a correct one.** Only resolution tests reference.
4. **Saving the session instead of the script.** Hidden state is created by re-running
   one cell.
5. **Pinning the environment and calling it reproducible.** It removes one of two
   failure terms.
6. **Acknowledging rather than citing.** Acknowledgements do not enter indexes.
7. **Citing the project, not the release.** The reader cannot tell which version
   produced your numbers.
8. **Quoting these synthetic numbers as repository or bibliometric statistics.** Every
   table describes a teaching generator.
