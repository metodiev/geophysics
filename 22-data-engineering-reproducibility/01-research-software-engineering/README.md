# Module 22-01 — Research Software Engineering

**Stages:** intermediate → graduate · **Prerequisites:** basic Python
([03-01](../../03-scientific-computing/01-python-fundamentals/README.md)) and a
first contact with Git
([03-13-06](../../03-scientific-computing/13-testing-profiling-packaging/06-git-workflow.md)).

This module treats the program as part of the apparatus. A computational result
is produced by a chain of decisions — how the code is structured, which version
ran, who reviewed it, what it documents, under which licence it may be reused and
how it is cited — and every one of those decisions is part of the method by which
the number was obtained. The module makes those decisions explicit and, wherever
possible, measurable, so that a reader can check not only what was computed but
also whether the computation can be trusted, re-run and credited.

The organising idea is **design for the second user**. The first user of research
code is its author, who holds the context in their head; the second user is a
reader, a reviewer, a new student or the same author a year later, and has none of
it. Every lesson is therefore written from the second user's position: a module
graph is read through the blast radius of a change rather than through its
elegance, a version-control history is read through the conflict probability of a
branch cadence rather than through the tidiness of the log, a review is read
through the escape rate of a change size rather than through the number of
reviewers, documentation is read through the fraction that is *accurate* rather
than the fraction that exists, and a release is read through the identifier and
licence that make it reusable instead of through its announcement.

All the measurements in this module are **SYNTHETIC**. The module graph, the
branch history, the review model, the documentation decay and the citation curve
are generated by the demonstrations with chosen parameters and a fixed seed
(`np.random.default_rng(20261014)`); no repository is parsed, no defect database
is read, no citation index is queried and no legal advice is given. Where a fact
is a matter of standard practice or documented compatibility — the behaviour of a
three-way merge, the default copyright position, a licence incompatibility — the
lesson says so and names the authority to check.

## Learning objectives

By the end of this module you will be able to:

1. Reason about a codebase structurally: compute coupling, fan-in, blast radius
   and instability, and predict which changes are expensive.
2. Use a version-control history deliberately: choose merge or rebase, set a
   branch cadence from a measured conflict probability, and recover work without
   rewriting shared history.
3. Review numerical and data code against a checklist of the defects that matter,
   quantify a review's detection and escape rates, and size a change for review.
4. Write documentation that states units, shapes and failure modes; keep a README
   that lets a stranger install, run, cite and distrust the code appropriately.
5. Place a release legally and creditably: classify licences, audit a dependency
   tree for distribution obligations, write a `CITATION.cff` and a
   software-availability statement.
6. Measure rather than assert the health of these practices, and state the
   regime in which each measurement is valid.

## Suggested path

**If you write analysis scripts and nothing has ever been reviewed:** read 01 §3–4
(what a change costs), then 02 (how to stop losing work), then 03 §7 (the
numerical-code checklist). That is the shortest path to a change in practice.

**If you are preparing a release for a paper:** read 04 and 05 in that order, then
05 §8 (the release checklist) with 02 §6. Those three sections are the difference
between an archive and a citable instrument.

**If you are setting up a group's conventions:** read 01 §6, 02 §6, 03 §4 and 05
§4, and write down the four conventions your group will actually follow — the
lessons give the arithmetic that makes each one defensible.

**If you are here for the measurements:** every lesson's demonstration is
self-contained; read the lesson's assumptions section before its results, and use
the ★★★ exercises, which ask you to design the measurement that would replace the
model with evidence.

## Mastery checkpoint

Complete this without notes, using the demonstrations only to check arithmetic:

> A group is about to publish a package that produced a paper's figures.
> **(a)** Their dependency graph has 60 modules and 101 edges with a maximum
> fan-in of 8. State the quantity that predicts the cost of their next change,
> and why the edge count alone does not. **(b)** Their release cycle is monthly;
> state the conflict probability for a branch that waits 30 days under the
> module's model, and the cadence you would recommend instead. **(c)** A
> 400-line pull request arrives. Compute the review time, the detection
> probability and the escape rate per KLOC under the module's model, and state
> what you would ask the authors to change before reviewing. **(d)** The README
> reports "documentation coverage 64 %". Name the measurement that answers
> whether the documentation can be trusted. **(e)** A dependency is under
> GPL-3.0 and appears in the published container image. State the licence the
> distributed work must carry, and one change that removes the obligation.

Worked versions of (a)–(e) appear in the lesson solutions at ★★ and ★★★ level.

## Common pitfalls across this module

1. **Optimising for the first user.** Every lesson's failure mode is the same:
   code, history, documentation and licensing that work for the person who
   already has the context.
2. **Quoting a number without its regime.** The 4.72-module blast radius, the
   0.22 conflict probability at 30 lines, the 59 % detection at 200 lines and the
   43.4 % accurate documentation are all model outputs; each lesson states the
   parameters they depend on.
3. **Treating a metric as a verdict.** A graph metric says where to read the
   code, a citation count says how much attention a package received, and neither
   says whether the number is correct.
4. **Adding artefacts without adding the discipline.** A `CITATION.cff` with a
   wrong author list, a licence named in the README but absent from the
   repository, or a docstring that repeats the code, are all worse than nothing
   because they invite trust they cannot support.
5. **Assuming reuse is somebody else's problem.** Licensing and citation are
   decided at release time and cost one file each; retrofitting them after a
   publication is expensive.
