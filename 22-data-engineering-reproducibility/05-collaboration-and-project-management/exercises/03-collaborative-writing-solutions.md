## ★1 — Why prose merges differently

A merge tool compares **lines**: in code a line is a statement, so a conflict marks a
coherent change, while in prose a line may be a whole paragraph, so two authors' edits to
different sentences collide on the same line. The LaTeX complication is that line breaks
are a formatting choice: re-wrapping a paragraph rewrites lines that carry no semantic
change, which inflates diffs and produces conflicts over formatting.

## ★2 — Line counts and diff sizes

(a) Hard-wrapped: $8000/12 = 667$ lines. Sentence per line: $8000/18 = 444$ lines.

(b) Ratio $= 444/667 = 0.67$ — the printed 0.67×.

(c) The **sentence-per-line** convention gives the smaller diff *per edit*, because an
edit's region is one sentence rather than a paragraph's worth of wrapped lines: changing a
sentence rewrites one line instead of five or six, and a merge therefore sees a smaller
region to conflict over. The total line count is not the quantity that matters.

## ★3 — Conflict probability versus separation

| Separation | Hard-wrapped prose | Sentence per line |
|---|---|---|
| 5 lines | 1.000 | 1.000 |
| 10 lines | 0.846 | 0.066 |
| 20 lines | 0.004 | 0.000 |

The explaining quantity is the **edit region's size**: conflict occurs when two regions are
closer than the diff's context, so a convention with smaller regions has a shorter conflict
distance.

## ★★4 — Five authors, 12 000 words

(a) Each author's 2 400 words (two sections of 1 200): hard-wrapped $2400/12 = 200$ lines;
sentences $2400/18 = 133$.

(b) Adopt **one sentence per line** (or semantic line breaks): with 133 lines per author
instead of 200, an edit region is a sentence, and two authors editing adjacent sentences
conflict over a shorter distance — the measured 0.066 against 0.846 at ten lines of
separation.

(c) The second convention: **one file per section** (or per chapter) so authors rarely
touch the same file at all. At that point conflicts become rare regardless of line breaks,
because the edits are separated by file boundaries rather than by lines.

## ★★5 — Four editors

(a) $P(\text{any}) = 1 - (1 - 0.7)^{8-1} = 1 - 0.3^{7} = 1 - 0.000219 = 0.9998$.

(b) The change that reduces it most: **assign sections to authors** (partition the
document), which replaces a shared region with owned regions. A secondary measure is the
sentence-per-line convention, which shrinks each edit's region.

(c) The mechanism is **proximity**: conflicts require regions closer than the merge
context, so partitioning the document moves the edits apart — and a file boundary is the
largest available separation. The arithmetic of §3 is what makes this quantitative rather
than a preference.

## ★★6 — What to track

(a) **Track**: LaTeX sources (the artefact), the `.bib` (a source under review), the
figure-generating code and its data identifiers (needed for reproduction), and any
permission or licence evidence. **Exclude**: the compiled PDF (a build product), `*.aux`
and `*.log` (regenerable intermediates), and the raw PNG figures *when* they can be
regenerated from code — keep them as release artefacts instead (they are useful for
reviewers and for the record).

(b) The two items that make the figures unreproducible: **figures with no code** (fix:
generate every figure from a tracked script, with the data identified) and **data named by
a mutable filename** (fix: record a dataset identifier and checksum, not
`final_data_v3.mat`). Both fixes are the same discipline as
[22-02-05](../../02-reproducible-workflows/05-data-versioning.md) §5.

(c) The submission's tag should point at a commit containing the sources, the figure code,
the `.bib`, the environment definition and the data identifiers — so the tag identifies a
*reproducible* version, not only the text.

## ★★★7 — A 40-page report, 12 authors, three institutions

**Layout.** `paper/main.tex` (or `main.md`), `paper/sections/01-intro.tex …`, `paper/figs/`
for generated figures, `code/` for the figure-generating scripts (or a reference to the
analysis repository), `bib/references.bib`, `env/` with a container or lock file,
`Makefile` with `make pdf` and `make figures`, `CONTRIBUTING.md` with the conventions.

**Conventions.** One sentence per line; one section per file with a named owner; no
reformatting in content commits; figures regenerated by `make figures`; references edited
only through the shared `.bib`; commit messages describing the scientific change.

**Build.** `make pdf` inside the pinned environment, producing a PDF with a build
identifier (the commit hash in the footer), so any PDF can be traced to its sources.

**CI checks.** Build the PDF (catches broken references and missing figures), regenerate
the figures from their code on a reduced input, check that no tracked file is a build
product (a guard against committing `*.aux`), and spell/consistency checks if the group
wants them.

**Figure regeneration.** Each figure's script writes its output into `paper/figs/`, and CI
verifies that the committed figure matches what the script produces (within a stated
tolerance for vector outputs) — the manuscript analogue of the regression tests of
[22-07-03](../../07-software-testing-quality/03-regression-testing-data.md).

**Review workflow.** Per-section reviewers; a pull request per section revision; the
reviewer reads the *diff* beside the compiled page; the issue tracker records the review
states ([22-05-02](../02-issue-tracking.md)).

**Artefact linking.** The submission tag, the analysis repository's release tag, and the
dataset identifiers are recorded in one table in `CONTRIBUTING.md` and in the paper's data
availability statement.

**What the design makes hard.** Authors who prefer a word processor: the conventions are
invisible in a `.docx`, and a co-author who does not use the repository will produce
suggestions as attachments, which is workable but slow. The honest mitigation is a
documented conversion path and a named integrator, not a demand that everyone change
tools mid-paper.

## ★★★8 — Measuring collaboration friction

**Data.** The commit history with per-file diffs and timestamps; conflict records (merge
commits with markers, or a tracker's log); author identities mapped to people (with
consent); and the document's word counts over time.

**Statistics.** (i) **Diff size per semantic change**: lines changed per commit divided by
the number of sentences meaningfully altered (estimable by inspecting a sample), which
exposes reformatting and re-wrapping; (ii) **conflict rate** per file and per week, against
the file's line count and the number of active editors; (iii) **time to merge** measured
from the last commit on a branch to the merge; (iv) the distribution of commit sizes, since
one 900-line commit hides more than twenty 45-line ones.

**Confounders.** Author habits (one co-author writes in long bursts; another edits
continuously) and deadlines (near a submission, everyone edits at once, so the conflict
rate spikes for reasons unrelated to the convention). Control by comparing within-author
and within-week, and by reporting the deadline weeks separately.

**What it cannot tell you.** Whether the *writing* improved: a repository can have tiny
diffs and an unclear argument. The measurement is about collaboration mechanics; the
paper's quality is a scientific judgement.

## ★★★9 — Migrating mid-paper

**Conversion steps.** (i) Freeze the current version as the reference (a tagged PDF and a
copy of the word-processor file), so nothing is lost if the migration stops; (ii) convert
the text to LaTeX or Markdown with a converter, then repair by hand — equations, tables and
cross-references need manual work in every converter tried; (iii) move the figures to
generated code where possible, and keep the rest as versioned images; (iv) put the
bibliography into a shared `.bib`; (v) commit the converted sources and build the PDF to
check that it matches the reference.

**Conventions to adopt immediately.** One sentence per line, one section per file, section
owners, and no reformatting commits. Add these *before* the migration so the converted
text is already in reviewable shape.

**Training needed.** A 60-minute session for co-authors covering: clone, edit, commit,
pull, resolve a conflict, and build the PDF — with a sandbox repository they can break. The
metric of success is that a co-author completes one full cycle unaided.

**Risks.** A lost week before a deadline is the real one: conversion plus repair is
unpredictable, and the deadline does not move. Mitigate by migrating between submissions,
by keeping the reference version alive, and by not converting the sections that are
already final.

**Abandon criterion.** Abandon the migration if the converted build does not match the
reference within the time reserved for it, or if a co-author's cycle (edit → commit →
build) cannot be completed unaided before the deadline window: the purpose of the change
is to reduce friction, and a migration that consumes the writing time fails on its own
criterion. State the reserved time (say two days) in advance, so the decision is arithmetic
rather than a matter of mood.
