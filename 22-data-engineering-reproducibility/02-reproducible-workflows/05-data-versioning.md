# Data Versioning and Provenance Tracking

## Learning objectives

By the end of this lesson you will be able to:

1. **Define** a data version as an immutable, identified snapshot, and **distinguish**
   it from a filename or a timestamp.
2. **Explain** content addressing, and **compute** the storage of a version series
   with and without chunk-level deduplication.
3. **Measure** which versions are cheap and which are expensive, and **state** what
   that implies for storage planning.
4. **Record** provenance as a derivation graph, and **state** the five fields an
   output must carry to be traceable to its inputs.
5. **Compute** the ambiguity that a missing version identifier creates, and **justify**
   the cost of recording one.
6. **Design** a versioning practice for a group's data that survives the loss of the
   working directory it was written in.

Storage and deduplication numbers in this lesson are **SYNTHETIC**: the version
series is generated by the demonstration with chosen edit rates, and the storage
figures are properties of that model. No archive, catalogue or repository was
queried and no real dataset was versioned.

## 1. Intuition: the largest unversioned part of the method

Code is versioned almost universally; data are versioned rarely. Yet the data decide
more of a geophysical result than the code does: a catalogue's completeness, a grid's
processing level, a station list's correction state. The usual practice — a directory
of files named with dates, edited in place — has neither identity nor history: two
files with the same name can hold different content, and no tool can say which
version produced a figure.

A **version** is an immutable snapshot with an identifier. Everything else in this
lesson follows from two properties of that definition: *immutability* means the
identifier never lies (rewriting the content creates a new version rather than
changing an old one), and *identification* means a figure can name exactly what it
consumed.

## 2. What an identifier must survive

An identifier serves three consumers, and each imposes a requirement:

| Consumer | Requirement |
|---|---|
| A script that reads the data | resolvable without human knowledge of a path |
| A paper's figure | stable and citable for years |
| A future analysis | verifiable: the content matches what the identifier asserted |

Three identifier kinds are used in practice and they are complementary:
a **content hash** (verifiable, not human-readable), an **archive DOI** (citable,
resolvable, third-party-kept), and a **release tag with a manifest** (convenient,
and only as durable as the repository). The robust practice records all three:
the DOI in the paper, the hash in the manifest, the tag in the repository.

## 3. Content addressing and deduplication

**Content addressing** stores data under a name derived from its content: the file
or chunk is hashed, and the hash is the key. Two consequences follow:

1. **Immutability is enforced**, because changing the content changes the key.
2. **Duplication is removed**, because identical content has the same key and is
   stored once.

For a series of versions, the storage saved depends on the granularity. The
demonstration's **SYNTHETIC** model is a $200 \times 200$ float64 grid (320.0 kB per
version) versioned 50 times, with each small version editing a $30 \times 30$ block
and every tenth version reprocessing the grid entirely. The data are addressed in
$25 \times 25$ chunks (5.0 kB each, 64 chunks per version):

$$S_{\text{naive}} = 50 \times 320.0\ \text{kB} = 16.00\ \text{MB},$$
$$S_{\text{CAS}} = 514\ \text{chunks} \times 5.0\ \text{kB} = 2.57\ \text{MB},$$
$$\text{deduplication ratio} = \frac{16.00}{2.57} = 6.2\times.$$

The mechanism is visible in the per-version table: a small block edit changes about
four to six chunks, while a reprocessing changes all 64. Across the 50 versions the
mean is **10.5 new chunks of 64 (16 %)**, so **84 % of each version is a reference to
content that already exists**.

## 4. Which versions are expensive

The per-version measurements separate two kinds of change:

| Kind of version | New chunks | Share of the version |
|---|---|---|
| First version | 64 | 100 % |
| Block edit | 4–6 | 6–9 % |
| Full reprocessing | 64 | 100 % |

The planning consequence is direct: storage grows with the number of
**reprocessings**, not with the number of versions. Twenty small edits after a
reprocessing cost about as much as one more reprocessing, whereas a pipeline that
regenerates the whole grid every night buys 320 kB per day for a single model. The
design rule is to make reprocessing versions explicit and rare, and to let the
steady stream of edits be genuinely incremental.

A second, subtler consequence: deduplication is **only as good as the chunking**. A
block edit of $30 \times 30$ cells touches four chunks of $25 \times 25$ because the
block crosses chunk boundaries; had the grid been chunked at $30$, the same edit
would touch one chunk and the ratio would rise. Chunking is a parameter of the
storage design chosen with knowledge of the access and edit pattern, not a neutral
default.

## 5. Provenance: the derivation graph

Versioning answers *which data*. Provenance answers *which processing*, and it is
recorded as a graph in which each version names its parents. In the demonstration's
model, version 50 has **49 direct ancestors** along the chain, with full
reprocessings at versions 10, 20, 30 and 40 — four points at which the chain was
deliberately broken and the whole grid recomputed.

Each recorded derive step should carry five fields, and a step missing any of them
is not traceable:

1. **Inputs**, by version identifier (never by path).
2. **The code**, by commit hash or release tag.
3. **Parameters**, explicitly, including seeds.
4. **The environment**, by lock-file hash or image digest
   ([22-02-02](02-environment-pinning.md)).
5. **The output**, by its own content hash.

The graph is what allows a question that version numbers alone cannot answer: not
"which data version is current" but "what would change if this catalogue version
were different", which is answered by walking the descendants of the affected node.

## 6. Ambiguity, and what recording costs

Without a recorded version, a figure's inputs are an unordered set. In a series of
50 versions the probability of guessing the right one is

$$\frac{1}{50} = 0.02\ (2\ \%),$$

and the cost of removing that ambiguity is **2 characters** in the figure's
metadata — the version index, or a short hash prefix. There is no other engineering
decision in this module with a comparable ratio of benefit to cost. The recording
belongs in the artefact that a reader will read: the figure caption, the notebook's
manifest, the pipeline's output log, or the data-availability statement of the paper.

## 7. Practice: versioning rules for a group

1. **Never edit a versioned file in place.** Write a new version; the discipline is
   what makes the identifier trustworthy.
2. **Version at write time, in the pipeline.** A rule's output is published to the
   store as part of the rule, so versioning is not a manual afterthought.
3. **Checksum every artefact.** A hash recorded next to the artefact turns a
   directory into a verifiable archive, and it is what makes the identifier checkable
   years later.
4. **Distinguish derived from observed data.** Observed data are irreplaceable and
   need archival practice; derived data can be regenerated and need only the
   provenance record that lets you regenerate them.
5. **Keep a manifest per release.** One file listing, for every artefact, its
   identifier, kind, size and the code version that produced it.
6. **Record the identifier where the reader looks.** In the figure caption, the
   README, and the data-availability statement — not only in the pipeline's log.
7. **Plan storage from the reprocessing rate, not the version count.** In the
   demonstration's model the ratio of naive to deduplicated storage is
   $6.2\times$; a different edit pattern gives a different ratio, and the number to
   forecast is the reprocessing count.

## 8. Worked example: a figure with no data version

A paper's figure was produced from "the gravity catalogue (2021 update)", and the
authors' repository contains the analysis code but no data copy and no identifier.
Work through it:

1. **Can the figure be reproduced?** No. The catalogue is a moving target: even if
   the same institution's file exists today, its content has been updated since, and
   nothing in the repository can detect a difference.
2. **What is the minimum repair?** An identifier and a checksum for the exact file
   used, recorded in the data-availability statement, even if the file cannot be
   redistributed — many catalogues can be identified by version and query date
   without being redistributed.
3. **What storage would the repair have needed?** In the demonstration's model, the
   deduplicated store holding 50 versions of the grid costs 2.57 MB against 16.00 MB
   naive: versioning is not the expensive part of an analysis, and the choice to skip
   it was not a storage decision.
4. **What does the identifier not fix?** A wrong processing step. The provenance
   record says what ran; it cannot say that the processing was appropriate.

## Assumptions and regime of validity

1. **Chunk-level deduplication is the model.** Object stores, Git-annex-style
   tools and DVC-style systems differ in their granularity and in whether deltas or
   chunks are stored; the numbers depend on the chunk size and the edit locality.
2. **Block edits are localised.** The model's edits touch a contiguous block; a
   workflow that perturbs scattered cells across the grid would change nearly every
   chunk and approach $1\times$ deduplication.
3. **Identical content means identical hash.** Cryptographic hashes make collisions
   negligible for this purpose, but the property is probabilistic, not mathematical.
4. **Provenance is only as complete as the recording.** The graph records what the
   pipeline declared; manual steps outside it are absent, which is the same
   undeclared-input failure as
   [22-02-03](03-workflow-managers.md) §8.
5. **The 2 % ambiguity figure is arithmetic, not a measured error rate.** It says
   what an unordered set of 50 versions implies, not how often analysts guess wrong.

## The honest summary

Data versioning is the practice of giving the largest part of a method an identity:
an immutable snapshot with a hash, a citable identifier and a recorded place in a
derivation graph. Content addressing makes it affordable — the demonstration stores
50 versions of a 320 kB grid in 2.57 MB, a $6.2\times$ saving on naive copies, because
a small edit adds only about 10.5 new chunks of 64 (16 %) — and the storage that
matters is set by the number of full reprocessings, not by the number of versions.
Provenance is five fields per step (inputs, code, parameters, environment, output)
and it answers the question version numbers cannot. Recording the identifier costs
two characters and removes a 98 % chance of guessing wrong about which of 50 versions
produced a figure. None of it establishes that the processing was right; it
establishes that you can find out what it was.

## Mastery checkpoint

Without notes: a group versions a 4 GB gridded product 120 times a year. Twenty of
those versions are full reprocessings; the rest are regional updates touching about
5 % of the grid.

1. Compute the naive annual storage and, assuming chunk-level deduplication with
   chunks sized so that a regional update touches 10 % of the chunks, the
   deduplicated storage.
2. State which of the 120 versions drive the storage, and what the group should
   change to reduce it.
3. State the five provenance fields for one of the regional updates.
4. A reviewer asks "which data version is figure 2 from?" and the answer is "the May
   one". State the two properties the answer lacks.

## Common pitfalls

1. **A filename is not a version.** Two files with the same name can hold different
   content, and no hash is recorded to tell you.
2. **Editing a versioned file in place.** It breaks the identity that makes the
   identifier useful.
3. **Forecasting storage from version count.** In the model, 50 versions cost
   2.57 MB against 16.00 MB naive; reprocessings, not versions, are the driver.
4. **Chunking without reference to the edit pattern.** A chunk size that straddles
   the edits inflates stored bytes (a $30 \times 30$ edit touching four
   $25 \times 25$ chunks).
5. **Recording identifiers only in logs.** The reader looks at the figure, the README
   and the paper; the identifier belongs there too.
6. **Confusing versioning with provenance.** A hash says which bytes; only the
   derivation graph says which processing.
