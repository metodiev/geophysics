# Spatial Databases and PostGIS

## Learning objectives

By the end of this lesson you will be able to:

1. **Explain** why a bounding-box query without a spatial index costs the whole table,
   and **compute** that cost.
2. **Choose** a tile or grid size from the query extent, and **measure** the candidate
   reduction it achieves.
3. **Compute** spherical and planar distances, and **state** the separation at which the
   planar approximation exceeds a stated tolerance.
4. **Estimate** the candidate pairs a spatial join produces, and **explain** why a
   neighbouring-tile rule is still required.
5. **Design** a spatial schema with the right geometry type, coordinate reference
   system and index for a stated query.
6. **Diagnose** a spatial query that returns wrong results because of a coordinate
   reference system mismatch.

Numbers in this lesson are **SYNTHETIC**: the point set is generated by the
demonstration, the tile model uses chosen tile sizes, and the distance comparisons are
computed exactly from a spherical formula. No spatial database was queried and no real
station catalogue is used.

## 1. Intuition: locality is the index

A relational index makes a *value* cheap to find. A spatial index does the same for a
*place*, and the argument is identical: without one, a query that returns 1 850 points
must test 200 000. The demonstration's **SYNTHETIC** point set — 200 000 points spread
over an $11° \times 10°$ region — returns 1 850 points for a $1° \times 1°$ box, which
is 0.91 % of the area of the region and requires **0.20 million point tests** without an
index. With one, the cost should scale with the answer, not the table.

Spatial indexing also introduces a complication that value indexing does not have: the
query predicate is a *region*, not an equality, so an index can only produce
**candidates** and a refinement step decides membership. Every spatial index is
therefore a two-stage filter, and the interesting quantity is the **candidate ratio** —
candidates divided by hits.

## 2. Tiles: choosing the grid

The demonstration models a uniform grid of tiles over the region and counts the points
in the tiles a $1° \times 1°$ query box touches:

| Tile (deg) | Tiles in region | Candidates tested | Fraction of the table |
|---|---|---|---|
| 0.05 | 44 000 | 2 005 | 1.00 % |
| 0.10 | 11 000 | 2 200 | 1.10 % |
| 0.25 | 1 760 | 2 841 | 1.42 % |
| 0.50 | 440 | 4 091 | 2.05 % |
| 1.00 | 110 | 7 273 | 3.64 % |

The trade is visible: smaller tiles cut the candidates (2 005 against 7 273, a factor of
3.6) but multiply the index entries (44 000 against 110, a factor of 400). The useful
tile size is set by the **query extent**: a tile about a quarter to a half of the query
size keeps the candidate ratio near 1 while keeping the index small, which is the same
conclusion as the chunking argument of
[22-03-02](../03-data-formats-and-engineering/02-format-design-tradeoffs.md) §2.

Two refinements matter in practice. First, points are not uniformly distributed in
Earth data — they cluster on networks — so a uniform grid produces unbalanced tiles and
a tree-structured index (an R-tree or similar) adapts to the density. Second, an index
over *bounding boxes* of extended objects (fault traces, survey polygons) measures
overlap of boxes, so the candidate ratio is governed by object size rather than by
point density.

## 3. Distance: sphere or plane

Queries of the form "within 50 km" require a distance, and the choice of formula is a
silent source of error. The demonstration compares the spherical (haversine) distance
with a locally scaled planar approximation:

| Separation | Spherical (km) | Planar (km) | Error |
|---|---|---|---|
| 0.01° | 1.05 | 1.05 | 0.000 % |
| 0.10° | 10.47 | 10.47 | 0.000 % |
| 1.00° | 104.52 | 104.52 | 0.001 % |
| 5.00° | 517.47 | 517.60 | 0.025 % |
| 20.00° | 1 982.79 | 1 991.93 | 0.461 % |
| 45.00° | 4 044.66 | 4 166.67 | 3.017 % |

The planar approximation is excellent to a few hundred kilometres (0.001 % at
$1° \approx 104$ km) and reaches 3 % at 45° — larger than many stated uncertainties, and
in a direction (overestimation) that is consistent, so it does not average out. The rule
is to state which formula a tolerance assumes; a "within 50 km" query with a planar
formula whose local scale factor is chosen for a different latitude can be wrong by
kilometres without any error appearing.

The subtlety that makes this a *spatial-database* question is the coordinate reference
system. A database may store geometry in a projected system (metres) or in geodetic
coordinates (degrees); distance functions operate in whatever system the geometry
carries, so a distance computed on degrees is meaningless and a distance computed on a
projection is valid only inside the projection's area of use. The mismatch is silent:
the query runs, the numbers look plausible, and the answer is wrong by the projection's
scale factor.

## 4. Spatial joins and candidate pairs

A spatial join between two point sets is a pairwise proximity test, quadratic by
construction: the demonstration's 200 000 and 100 000 points give
$2 \times 10^{10}$ pairs without an index. Keying both sets by tile and joining within a
shared tile reduces the candidates to **11.36 million** — a factor of **1 760**.

Two cautions. First, the tile rule as stated misses **cross-boundary** pairs: two points
30 m apart on opposite sides of a tile edge are in different tiles. Any real
implementation therefore searches a point's tile **and its neighbours** (or uses an
index that handles the boundary), which multiplies the candidate count by up to nine in
the worst case — the reduction is real but smaller than the shared-tile figure suggests.
Second, the candidate count is not the cost: each candidate still undergoes the exact
distance test, and the index's job is only to make that set small.

## 5. Designing a spatial schema

1. **Geometry type.** Points for stations and events; linestrings for traces; polygons
   for survey areas. The type decides the index that can be built and the predicates
   available.
2. **Coordinate reference system, declared.** Store geometry with its system explicitly,
   and state whether the storage is geodetic (degrees) or projected (metres). Record the
   datum, not only the projection name.
3. **Index.** A spatial index on the geometry column for containment, overlap and radius
   queries; a composite index where the workload also filters on time or magnitude, so
   that the planner can use both.
4. **Summary columns.** Precomputed bounding boxes, a cell or geohash key, and a coarse
   location label make the common queries cheap without a spatial predicate at all —
   and a cell key is a plain value index, which is simpler to operate.
5. **Constraints.** Latitude and longitude ranges, geometry validity checks, and
   non-null constraints on the coordinate columns; a point with missing coordinates is
   the spatial analogue of a missing key.

## 6. Practice

1. **Index before you complain.** A bounding-box query with no spatial index is a scan
   with extra steps.
2. **Refine:** use the index to get candidates, then an exact predicate. Never treat an
   index hit as a result.
3. **Neighbour the tiles** in a custom grid implementation, or use a tree index that
   handles boundaries.
4. **State the formula and the system** for every distance: spherical or planar, and in
   which reference system.
5. **Test with known pairs.** A handful of point pairs with independently known
   distances (a few metres to a few thousand kilometres) is the cheapest regression test
   for a spatial predicate, and it is the subject of
   [22-07-03](../07-software-testing-quality/03-regression-testing-data.md).
6. **Beware antimeridian and poles.** A longitude range like $170°$ to $-170°$ is a
   two-part interval, and a planar approximation near the poles is useless; both are
   silent without a test.

## 7. Worked example: a radius query that returns the wrong stations

A query asks for stations within 25 km of a site, using a planar formula with a scale
factor computed once for the study area's centre.

1. **Check the scale factor.** At the centre it is exact by construction; 500 km away the
   factor differs by a fraction of a per cent, so a 25 km radius is off by tens of
   metres — usually acceptable.
2. **Check the units.** If the station coordinates are stored in degrees and the formula
   treats them as kilometres, the answer is wrong by a factor of about 111 — the plan
   would show a scan and the result set would be nonsense, but only a sanity check of the
   distance would show it.
3. **Check the reference system.** If the stations are in a projected system (metres) and
   the site is given in degrees, the comparison is between metres and degrees: the query
   runs and returns the wrong stations silently, which is the failure §3 warns about.
4. **Check the boundary.** Stations just outside the radius pass the bounding-box
   pre-filter (correctly) and must be excluded by the exact distance test; a query that
   omits the refinement returns them.

The diagnosis in all four cases comes from the same practice: a set of known pairs, run
as a test, with the formula and the reference system stated in the test's name.

## Assumptions and regime of validity

1. **Uniform point density.** The tile table assumes uniform density; real networks
   cluster, so a uniform grid is unbalanced and a tree index is preferable.
2. **Chosen tile sizes.** The candidates are computed from the grid model, not from a
   database's index; the reduction factor is indicative.
3. **Spherical Earth for the reference distance.** The haversine formula assumes a
   sphere of radius 6371.0088 km; an ellipsoidal distance differs by up to about 0.5 %
   depending on latitude and azimuth, which matters when a tolerance is tight.
4. **Planar approximation with a locally scaled factor.** The comparison uses a
   mean-latitude scaling, which is the best simple case; other scalings are worse away
   from their reference latitude.
5. **No index implementation was benchmarked.** R-trees, grids and geohash schemes differ
   in their candidate ratios and update costs; the lesson gives the argument, not a
   ranking.

## The honest summary

Spatial lookups are the same access-path problem as value lookups, with a region instead
of an equality: without an index a $1°$ box costs 0.20 million point tests for 1 850
hits, and a tile grid cut the cost to about 1 % of the table at a tile of $0.05°$ or the
same hits at a coarser tile with far fewer index entries. Candidate reduction is the
metric, and it is always approximate — a neighbouring-tile rule is required for
correctness at boundaries, and an exact refinement step decides membership. Distances
must state their formula and their reference system: the planar approximation is within
0.001 % at 100 km and 3 % at 5 000 km, and a coordinate-system mismatch is wrong by the
projection's scale factor with no error message. Spatial joins benefit most: 20 billion
pairs become 11.36 million candidates, a factor of 1 760, before the refinement test.

## Common pitfalls

1. **No spatial index.** The query returns the right rows after testing the whole table,
   which is why it is easy to ship and expensive to run.
2. **Treating an index hit as a result.** The index produces candidates; the refinement
   predicate decides.
3. **Ignoring tile boundaries.** A shared-tile join misses pairs across edges.
4. **Degrees treated as metres.** Distances wrong by a factor near 111, silently.
5. **A planar formula far from its reference latitude.** 3 % at 45° of separation,
   in a consistent direction.
6. **Antimeridian and polar queries.** A longitude interval that wraps, and a planar
   approximation near the poles, both fail without a test.
