# Scientific File Formats: CSV, Parquet, HDF5, netCDF, Zarr

## Learning objectives

By the end of this lesson you will be able to:

1. **State** what a scientific file must carry beyond its numbers — shape, type,
   units, coordinates and provenance — and **judge** a format by that list.
2. **Compute** the size of the same data in text and binary representations, and
   **measure** the round-trip error of a chosen number of decimals.
3. **Estimate** parse cost from a throughput model, and **explain** why text costs
   much more time than bytes alone would suggest.
4. **Choose** among CSV, Parquet, HDF5, netCDF and Zarr for a stated access pattern,
   and **name** the cost that comes with each choice.
5. **Design** a conversion between representations that preserves shape, dtype,
   units and provenance, and **verify** it with a round trip.
6. **Diagnose** the two silent failure modes of a format conversion: precision loss
   and lost metadata.

All size, precision and timing numbers in this lesson are **SYNTHETIC**: the array
is generated by the demonstration and the cost model uses chosen throughput
constants. No real file was written, read or compressed, and no benchmark of a real
library is quoted.

## 1. Intuition: the file is part of the data

A number in a file is not a measurement until it is accompanied by what it means: a
shape, a dtype, a unit, a coordinate system, a time stamp, and the processing that
produced it. A format is the container that carries all of those things — or fails
to. The choice of format is therefore a modelling decision about the data set, not
a storage preference, and the failure of a format choice is usually silent: the
numbers arrive, and the meaning does not.

The practical test is: **can a reader who has never spoken to you recover the
meaning of these bytes from the file alone?** A CSV usually fails that test; a
self-describing format usually passes it; and a binary dump without a schema passes
it only if the schema exists somewhere else that is also archived.

## 2. What a scientific file must carry

| Item | Why it is needed | Commonly lost by |
|---|---|---|
| Shape and dtype | to interpret the byte stream | raw binary dumps |
| Units | to compare with anything | CSV headers written as prose |
| Coordinates | to locate values in space and time | arrays without axes |
| Missing-value convention | to distinguish gap from zero | CSV with empty fields |
| Provenance | to know the processing state | every format, unless written explicitly |
| Compression and chunking | to make the access pattern cheap | format defaults |

Only items 1 and 5 are truly format-level; the rest require discipline inside
whatever container is chosen. This is why "we use netCDF" is not, on its own, a
metadata strategy.

## 3. The same numbers in different representations

The demonstration generates 250 000 values from a unit-variance **SYNTHETIC**
Gaussian and produces four representations:

| Representation | Bytes | Bytes per value | Size relative to float64 |
|---|---|---|---|
| text, 6 decimals | 2 375 126 | 9.50 | 1.19× |
| text, 3 decimals | 1 625 126 | 6.50 | 0.81× |
| binary float64 | 2 000 000 | 8.00 | 1.00× |
| binary float32 | 1 000 000 | 4.00 | 0.50× |

Two results matter. First, **text is not smaller**: six decimals cost 19 % *more*
than the binary64 payload. Second, **float32 halves the size at a real cost in
precision**, and that trade is available in either representation.

The precision question has a clean answer measured by the round trip. Re-parsing
the text at $d$ decimals gives a maximum absolute error:

| Decimals | Max round-trip error (data units) | Values whose bits change |
|---|---|---|
| 3 | $5.00 \times 10^{-4}$ | 20 000 of 20 000 |
| 6 | $5.00 \times 10^{-7}$ | 20 000 of 20 000 |
| 9 | $5.00 \times 10^{-10}$ | 20 000 of 20 000 |
| 12 | $5.00 \times 10^{-13}$ | 19 998 of 20 000 |

For comparison, the float32 rounding floor for the same data is
$2.23 \times 10^{-7}$. So writing six decimals to a text file is comparable in
error to storing float32, and writing twelve decimals *still* changes bits for
almost every value: text is a lossy representation unless the number of decimals is
chosen from the data's own scale $(\text{range}, \text{uncertainty})$ rather than
by habit. The rule that follows: write enough decimals that the round-trip error is
well below the measurement uncertainty, and say what you chose.

## 4. The cost of reading text

Parsing dominates. With the demonstration's chosen throughputs — 60 MB/s for text
parsing, 2000 MB/s for binary unpacking, fixed open/close overhead excluded — the
same 250 000 numbers cost:

| Representation | Size (MB) | Parse time (s) | Relative to binary64 |
|---|---|---|---|
| text, 6 decimals | 2.38 | 0.0396 | 39.6× |
| text, 3 decimals | 1.63 | 0.0271 | 27.1× |
| binary float64 | 2.00 | 0.0010 | 1.0× |
| binary float32 | 1.00 | 0.0005 | 0.5× |

Text costs tens of times more time than binary for the same content, because each
value must be tokenised, converted and validated. The consequence for a pipeline is
that format choice appears in the *wall time* of every run, not only in the storage
bill, and the effect compounds with the number of runs — which is exactly what the
caching of [22-02-03](../02-reproducible-workflows/03-workflow-managers.md) tries to
avoid.

## 5. Choosing among the families

| Format | Best at | Cost it imposes |
|---|---|---|
| CSV | human inspection, diffs, interchange of small tables | no types or units, larger, slow parse |
| Parquet | column-selective reads, compression, typed schema | write-once columnar layout; needs a library |
| HDF5 | hierarchical groups, partial reads, rich metadata | a complex format with version history; single-file contention |
| netCDF | self-describing arrays with geoscience conventions | conventions to learn; tooling heterogeneity |
| Zarr | chunked arrays on object stores, parallel writes | many small objects; needs a store and a plan |

The question to ask is not "which is best" but "which access pattern must be
cheap". A table read one column at a time wants Parquet; a gridded field read in
windows wants netCDF or Zarr with chunks matched to the window
([22-03-02](02-format-design-tradeoffs.md)); a 300-row station list that a
colleague must inspect wants CSV, and the loss of types is worth the interchange.
Mixing them is normal: CSV for the small parameter table, netCDF for the grid,
Parquet for the catalogue.

## 6. Self-describing data, and what "self" means

A format is *self-describing* when the file carries the metadata needed to read it:
dimensions, coordinates, variable names, units and attributes. Two practical
consequences:

1. **The metadata is versioned with the data**, so a reader in five years has it
   even if the documentation has rotted away.
2. **Metadata can be wrong**, and wrongly labelled metadata is worse than none:
   a netCDF file whose `units` attribute says `m/s` while the values are in `gal`
   produces a silent factor-of-100 error in every downstream analysis, as the
   metadata lesson quantifies ([22-03-06](06-metadata-standards.md)).

The discipline that keeps metadata honest is a **conversion round trip**: read the
file, write it in the target format, read it back, and compare values, shapes,
dtypes, units and coordinates. The comparison is cheap and it catches exactly the
two silent failures this lesson is about — precision loss and lost metadata.

## 7. Worked example: converting a catalogue to Parquet

A group has a 12-million-row CSV catalogue, queried mostly by station and time
range, and re-read on every run of a 30-minute pipeline.

1. **Size.** At the demonstration's 9.50 bytes per value for six-decimal text, a
   twelve-column row costs about 114 bytes; Parquet with dictionary encoding and
   compression typically stores the same content in a fraction of that. Measure on
   your own data: the compression return is data-dependent — the demonstration
   measures a $76.29\times$ ratio on a smooth ramp and $1.08\times$ on white noise.
2. **Parse cost.** The 39.6× ratio of §4 applies to the values; a 12-million-row
   CSV read at 60 MB/s takes about $1.4\ \text{GB} / 60\ \text{MB/s} = 23\ \text{s}$
   of parsing alone, against roughly a second for the columnar read of only the two
   columns the query needs.
3. **What is lost.** CSV fields have no types: a station code `007` becomes the
   integer 7 unless the schema says otherwise, and an empty field is
   indistinguishable from a missing one unless the reader was told. Both must be
   declared in the Parquet schema and checked by the round trip.
4. **What must be kept.** The units of every column, the time zone of the time
   stamps, the meaning of a missing value, and the file's provenance — which CSV
   export of which catalogue, with a checksum
   ([22-02-05](../02-reproducible-workflows/05-data-versioning.md) §5).

The conversion is worth doing once and measurable every run; the two failure modes
above are the ones to test for, because neither raises an error.

## Assumptions and regime of validity

1. **Throughputs are chosen constants.** Real text-parse and binary-read rates vary
   by an order of magnitude with the library, the dtype and the machine; the ratio
   is the durable result, not the absolute times.
2. **The synthetic array is Gaussian.** Round-trip error depends on the values'
   magnitude: values near zero lose relatively more precision at a fixed number of
   decimals, and coordinates stored as text are usually the place this bites.
3. **Compression ratios are data-dependent.** The demonstration measures zlib on a
   smooth ramp and on white noise precisely to make the point that a ratio cannot be
   assumed from the format name.
4. **No format comparison was benchmarked.** The family table describes design
   intent and costs; it does not rank libraries, whose performance depends on the
   access pattern.
5. **Text is not always wrong.** For small tables that humans inspect, diff and
   hand-edit, the loss of types and the parse cost are worth paying, and the lesson
   says so explicitly.

## The honest summary

A scientific file must carry shape, dtype, units, coordinates, missing-value
convention and provenance; the format decides how much of that is automatic. The
measurements are simple and decisive: text at six decimals is 1.19× the size of
binary64 and costs 39.6× the parse time, float32 halves the size at a rounding
floor of $2.23 \times 10^{-7}$, and even twelve decimals changes bits for 19 998 of
20 000 values. Compression returns are data-dependent (76.29× on a smooth ramp,
1.08× on noise). Choose the format that makes the required access pattern cheap,
write the metadata that the format cannot infer, and verify every conversion with a
round trip that compares values, shapes, units and coordinates — because the two
failures that matter, precision loss and lost metadata, are both silent.

1. Compute the bytes for text at 6 decimals, binary float64 and binary float32,

2. Choose a number of decimals and justify it against the stated uncertainty;

   and say where each should live.

   detects.

## Common pitfalls

1. **Assuming text is the small, simple choice.** At six decimals it is larger than
   binary64 and costs 39.6× the parse time.
2. **Choosing decimals by habit.** Three decimals gives a $5.0 \times 10^{-4}$
   error on unit-scale data — often above the measurement uncertainty.
3. **Trusting an unlabelled array.** A raw dump without a schema is a data set only
   if the schema is archived with it.
4. **Writing units in a free-text header.** A unit inside a comment is not metadata;
   no library can act on it.
5. **Skipping the round trip.** Precision loss and metadata loss are both silent
   without a read-back comparison.
6. **Assuming a compression ratio from the format name.** The same algorithm gives
   76.29× on a smooth field and 1.08× on noise.
